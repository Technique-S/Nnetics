## Independent gates and exact acceptance scope — 5 November update

The shared-gate blocker is fixed locally. Runtime gates remain disabled; no live test is authorized by implementation. The legacy `NNETICS_TRANSACTIONS_AUTHORIZED` variable is **ignored for authorization** and enables neither operation. Provisioning still uses its original independent `NNETICS_PROVISIONING_ENABLED` permission and all existing factory/owner checks.

| Configuration | Meaning |
| --- | --- |
| `NNETICS_OWNER_TRANSACTIONS_AUTHORIZED=testnet-reviewed` | Necessary but insufficient for owner signing: a valid reviewed scope file and exact hash are also required. It never starts a worker or changes chain authority. |
| `NNETICS_OWNER_TRANSACTION_PLAN` | Absolute path to the reviewed V2 acceptance JSON. Missing, malformed, oversized, unsupported, or mismatched configuration fails closed. |
| `NNETICS_OWNER_TRANSACTION_PLAN_SHA256` | Exact lowercase SHA-256 of that file. A hash is an integrity check, not wallet authentication or independent security approval. |
| `NNETICS_PAYMENT_EXECUTION_AUTHORIZED=testnet-reviewed` | Independent worker execution permission. Still requires complete configuration, explicit worker startup, fresh checkpoint, valid restricted key, eligible job and all vault/contract guards. Does not permit owner signing. |

Empty, missing or other values disable their gate. Public configuration exposes `ownerTransactionsEnabled` and `paymentExecutionEnabled` separately; the retained `transactionsEnabled` field is a compatibility alias **for owner signing only**. Health reports both owner permission and payment permission separately; these are configuration capabilities, not claims that chain readiness or permission checks passed. A change to flags, scope ID or scope-file hash invalidates the old client transaction context. Nothing is started by setting either variable. Hosted rollout guards reject nonempty owner/payment/scope configuration, and measurement/contractor fixtures strip all signing configuration.

Only the restricted Meteor storage-acceptance profile is currently supported by the owner gate. This is not unrestricted owner activation. The backend verifies the configured network, organization, signer, target and code hash against the authorized current owner. It accepts only `fund_storage({})`, exactly 0.000001 NEAR attached and 100 Tgas, built as exactly one action. Additional actions/properties, other methods, nonempty/altered arguments, amounts, gas, identities, networks or targets are rejected server-side. Dispatch independently decodes the canonical prepared bytes and checks their hash, signer, receiver, signing key, nonce, action count and action contents. Existing owner authorization and wallet-selected-account verification remain necessary. Native wallet review remains separate from login; no focus/navigation proof is added. General owner actions and alternate signing connectors are not allowed by this narrow profile.

The existing durable attempt remains exclusive during preparation and unknown outcomes. A new `owner_acceptance_uses` record is inserted **atomically with dispatch**, before Meteor can open. Its stable scope ID depends on the acceptance intent, not plan formatting, descriptive metadata, process lifetime or flag toggles. After dispatch it remains consumed through unknown outcome, wallet refusal, contract failure or success; verified terminal results move the attempt to history but do not rearm the scope. Before dispatch, a cancelled unsubmitted review can be prepared again. Read-only reconciliation of current or historical attempts does not require signing permission. Do not delete/roll back the durable database to reset an acceptance; flags and edited file hashes are not a reset mechanism.

Hardening found during this change: dispatching a missing/cancelled attempt previously returned null, which could be mistaken by a client for permission to continue. The server now rejects it, and the client requires a matching durable dispatch acknowledgement before opening the transaction interface. Gates, scope hash, session/key and review expiry are checked again after asynchronous preflight reads, before persistence/dispatch. Unknown actions are rejected. No automatic replacement or timeout unlock was added.

## Flow and safeguards

1. Existing execution/configuration gates and fresh authoritative snapshot verify testnet, code, current owner, organization and vault. Owner membership still comes from server authorization; wallet connection does not grant ownership.
2. The backend validates frozen owner-method arguments and deposits, derives the authenticated FullAccess key/nonce, estimates a bounded fee allowance, checks balance, constructs one NEAR transaction and persists its exact unsigned bytes/hash. Concurrent preparation is excluded by SQLite's unique organization/owner slot. Review is valid for three minutes.
3. An explicit review shows the owner, network, full contract, action/effect, exact deposit/amount, resolved agreement/payment recipient where applicable, fee allowance, expiry and transaction ID. Cancel before dispatch releases only that unsubmitted review. The read-only recovery panel can also cancel an interrupted unsubmitted review.
4. Continuing asks a fresh optional selected-account proof **for this financial action only**. A verified different account revokes the old session and clears protected views in all tabs; it never inherits ownership. Ordinary dashboard use still signs nothing. The client independently decodes/checks the prepared action and hash.
5. Immediately before Meteor opens, server dispatch rechecks owner/context, key, nonce, expiry, fees and protocol. The narrow acceptance rejects activation methods entirely; the worker's fresh-checkpoint safeguard is unchanged. A compare-and-swap and stable one-use consumption mark the attempt unknown before any sign-and-send request. Lost dispatch responses also remain held.
6. Meteor signs and broadcasts internally. A popup result is not confirmation. Backend reconciliation requires FINAL evidence matching hash, signer, target, key, exact nonce, method, arguments, deposit and gas. Only a verified terminal result moves to durable history and releases exclusion. A contract failure is shown separately from a wallet refusal or network timeout.

A post-dispatch refusal/disconnection is **not** proof that nothing was broadcast. It shows the wallet outcome separately while retaining unknown submission state. Clicks, refresh and process restart cannot create another attempt. Read-only status checks never request signatures. Different wallet-reported hashes are retained alongside the original pinned hash; neither is silently substituted. An append-only, unique `(attempt, hash)` table retains every report. Reconciliation fetches network evidence outside SQLite, then uses `BEGIN IMMEDIATE` to re-read the current durable attempt, merge reports and validate the expected transaction before atomically updating history/one-use consumption and deleting the exact active record. There is no await inside this transaction. Concurrent finalizers return the existing history entry rather than writing their stale snapshots. A conflict commits `manual_review` with `manualReviewRequired`, keeps the expected ID and all reported IDs, and never deletes the held attempt or rearms the consumed acceptance. Reports arriving after terminal finalization are owner/organization/contract checked against history; a conflicting report restores a held manual-review record and preserves the previous expected-transaction result. It does not restore permission to submit. Read-only checks and refresh display this hold and all IDs; no automated conflict-resolution/unlock path is supplied. There is deliberately no automatic expired-transaction unlock: unresolved or byte-changing wallets need explicit evidence review. This limitation may require a separate reconciliation enhancement if the installed extension rebuilds transactions; live compatibility is not yet accepted.

The fee allowance is `(100 Tgas + 2 Tgas overhead) × finalized gas price × 2`, capped at 0.022 NEAR, rechecked at dispatch. It is a conservative quote and owner stop condition, not a token-denominated fee cap enforced by the protocol. The gas limit is fixed at 100 Tgas. No floats or token `Intl.NumberFormat` are used.
