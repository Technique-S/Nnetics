## Stage B — contractor lifecycle

### B1 Store operations (`src/server/contractor-records.ts`)

`ContractorProfile` gains `archived: boolean` and `archivedAt: string | null` (persisted JSON,
backward compatible: old payloads read as not archived). New audit table
`demo_contractor_events(id, org, profile, profile_name, action, detail, at)`.

New `OwnerPortalCommand` actions, implemented only for the demo store (the live organization
store refuses them with an explicit message, so live behaviour is unchanged):

* `update-contractor` (rename)
* `archive-contractor` — sets `archived`, bumps `generation`, revokes every portal link
  (`demo_links.revoked=1`), clears `pendingWallet`, writes an audit event. Bills, orders and
  uploads are kept.
* `restore-contractor` — clears `archived`, writes an audit event.
* `delete-contractor` — allowed only when the contractor has no bills, no orders, no uploads and
  no active link. Otherwise it is refused and the archive option is offered. On success it
  removes the profile, its links and its wallet proofs in the existing single transaction.
  Payment records and receipts live in the separate demo workspace store and are never touched.

`ownerSnapshot` returns `profiles` (active), `archivedProfiles` and `events`. Each profile
carries a computed `deletable` flag used by the UI.

### B2 Contractor UI (`src/app/contractor-owner.tsx`)

Per-contractor action menu: **Edit contractor**, **Archive contractor**, and **Delete
contractor** only when eligible. Destructive actions require an explicit confirmation naming the
contractor and the consequence, e.g. "Delete Tia? This will permanently remove the contractor
profile and revoke associated portal access. This action cannot be undone."

### B3 Ask Nnetics

New tools `archive_contractor`, `restore_contractor`, `delete_contractor` (demo only,
`confirmationRequired: true`). The tool **prepares** a pending operation and performs no
mutation. New server module `src/server/contractor-lifecycle.ts` holds the pending operations
with their single-use confirmation secret, scoped to the owner session.

The secret never enters the model context: the tool result carries only the operation id,
contractor, eligibility and reason. The HTTP response's action chip carries the secret, so only
the browser can complete the operation. The model can never turn its own text into consent — the
runtime has no path from model output to the confirm endpoint, and the confirm endpoint
revalidates eligibility, permissions and expiry before executing once.

`UNSUPPORTED_OPERATIONS` drops the "no deletion or archive" statement.

### B4 Remove the three-contractor cap

Delete the `count.n >= 3` server check, the `N/3` counter and the disabled "Add contractor"
button. The tool description loses its "at most three" sentence. The Contractors list gains a
name search and incremental paging (25 per page).
